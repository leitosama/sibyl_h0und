# Шлюз отчёта: челленджер и репортёр на дайджесте улик

Дизайн, который объединяет [#45](https://github.com/leitosama/sibyl_h0und/issues/45)
(челленджер benign-вердикта) и [#39](https://github.com/leitosama/sibyl_h0und/issues/39)
(репортёр с компактным дайджестом). Дайджест и челленджер приняты в
[ADR 0022](adr/0022-benign-challenger.md); репортёр — пока гипотеза. Роли совпадают с кандидатами из
[architecture.md](architecture.md#роли): челленджер — «гипотезёр»,
репортёр — «IR-аналитик».

## Идея

Когда голова (основная модель) вызывает `finish_investigation`, её отчёт
становится **черновиком**. Дальше возможны два отдельных вызова LLM, каждый
со своим коротким контекстом, собранным из одного **дайджеста улик**:

- **Челленджер** (#45) — только на первый benign-черновик. Строит самую
  сильную версию атаки по тем же фактам и предлагает проверки, которые её
  опровергнут. Ответ уходит голове как локальный ответ на `finish_investigation`.
- **Репортёр** (#39) — на каждый черновик, который уходит в runtime. Пишет
  итоговый отчёт по дайджесту: артефакты, доказательства легитимности,
  `reasoning`.

Оба — разовые вызовы без инструментов и без цикла. Вызовов runtime они не
тратят.

```
голова: finish(черновик)
  │
  ├─ проверка ADR 0018 на черновике (пустой отчёт → один отказ, как сейчас)
  │
  ├─ benign, не режим «только отчёт», челленджа ещё не было
  │     └─ ЧЕЛЛЕНДЖЕР(алерт, дайджест, still_open) ──► локальный ответ голове:
  │          версия атаки, проверки, still_open
  │          (сбой → текущий BENIGN_CHALLENGE)
  │          голова смотрит дальше или сдаёт отчёт снова ─► наверх
  │
  └─ иначе
        └─ РЕПОРТЁР(алерт, дайджест, черновик, запись челленджа) ──► Send(отчёт)
             (сбой или негодный ответ → Send(черновик))
```

## 1. Дайджест улик (общая часть)

Новый модуль `digest.py`. Дайджест строит код из GraphLedger, без оценок:

- **Каждый объект, который вернул runtime, один раз**, со свойствами как
  есть. Сейчас ledger хранит только ключи свойств и сырые ответы по вызовам,
  поэтому нужно хранилище `objects: dict[id, dict]`, которое заполняет
  `_collect`.
- **Связи — рёбрами**: `source → type → target` со свойствами.
- **Группировка по хостам.** Хост — сущность графа (алерт всегда несёт
  `host` + `windows_process`). Объекты группируются под хост-сущностью, к
  которой они привязаны в графе; связи между хостами идут отдельным блоком
  «между хостами» — там видно латеральное перемещение. Внутри группы —
  обход в ширину от триггера алерта. Если хост-сущностей нет или объект ни к
  одному хосту не привязан, он попадает в общую группу в порядке обхода.
  Имя типа хоста — единственная константа; если на зачёте оно другое,
  дайджест деградирует до обхода в ширину, но не ломается (ADR 0003). Как
  именно процесс привязан к хосту (связь или свойство), первым делом
  проверяем по трейсам.
- **`still_open`** из `GraphLedger.summary()` как есть — отсюда «180 связей,
  3 открыты».
- **Не входит:** обёртки ответов, повторы одного объекта, `note` и
  `still_open` из прошлых ответов, ответы `lookup_knowledge`, рассуждения
  головы.

Для id и свойств дайджест без потерь: сжимает только повторы и обёртки.
Правило ADR 0007 «каждый id остаётся доступен для отчёта» сохраняется.
«Ключевые свойства» дайджест не выбирает: какие свойства важны, решает
модель (ADR 0017).

## 2. Устройство: `Investigation` остаётся владельцем (ADR 0016)

`before_call` остаётся синхронным и получает третий вид ответа рядом с
`LocalAnswer` и `Send`:

```python
@dataclass(frozen=True)
class Review:
    role: str  # challenger, потом reporter
    arguments: dict[str, Any]  # подготовленные аргументы finish
    messages: list[dict[str, Any]]  # запрос побочного хода, собирает Investigation
    response_format: dict[str, Any]
    model: type[BaseModel]
```

Цикл агента делает только ввод-вывод: выполняет побочный вызов и отдаёт
разобранный результат (или `None` при сбое) в
`investigation.after_review(review, result)`, который возвращает
`LocalAnswer` или `Send`. Промпты, формулировки, фолбэки и события трейса
остаются в `Investigation` и новом модуле.

В `llm.py` рядом с `next_step` появляется общий метод, например
`structured(messages, response_format, model, role, trace)`: тот же
ограниченный цикл повторов и ремонта с таймаутом каждого запроса (ADR 0009).
Любая ошибка побочного хода ведёт к фолбэку, а не к остановке задачи.

## 3. Челленджер (#45)

- **Вход:** алерт, дайджест, `still_open`. Текста головы не видит.
- **Ответ:** `{hypothesis, checks: [{refuted_if, call: {tool, ...аргументы}}]}`,
  от 1 до 3 проверок. `tool` — из каталога задачи, id проходят `ledger.is_known`.
  Негодные проверки отбрасываются; если не осталось ни одной — фолбэк.
- **Голове:** версия, проверки и `still_open`. Промпт просит в следующем
  состоянии ответить на каждую проверку: проверено вызовом X / опровергнуто
  уликой `<id>` / проверить нельзя.
- Malicious не оспаривается, в режиме «только отчёт» челленджа нет, один раз
  за задачу — как в ADR 0020.
- Промпт — только из общих принципов: взгляд атакующего на те же факты и
  проверки, которые его опровергнут. Никаких примеров, программ, портов,
  типов связей и сценариев из трейсов `practice`.

## 4. Репортёр (#39)

- **Вход:** алерт, дайджест, черновик головы (вердикт, ссылки, `reasoning`),
  запись челленджа и ответ головы на него, если челлендж был.
- **Ответ:** схема finish из каталога задачи
  (`catalog.response_format([FINISH_TOOL])`), так что другая форма отчёта на
  зачёте тоже работает (ADR 0003, 0014).
- **Вердикт фиксирован.** Репортёр — роль результата: его задача — чтобы
  отчёт был верным и полным для уже вынесенного вердикта. Промпт называет
  вердикт; ответ с другим вердиктом считается негодным, и уходит черновик.
  Это проверка ответа репортёра, а не вето на вердикт расследования.
- **Проверка:** `ledger.check` по id и проверка ADR 0018. На неизвестный id
  репортёр получает один ход ремонта, после него уходит черновик. Черновик
  эти проверки уже прошёл, поэтому фолбэк всегда можно отправить.
- **Режим «только отчёт»:** репортёр работает. Здесь он полезнее всего —
  контекст головы самый длинный.

## 5. Трейсы и ADR

- У `llm_call` поле `role` (`head`, `challenger`, потом `reporter`), и
  `prefix` считается от прошлого запроса той же роли: иначе после побочного
  хода история головы записывалась бы в трейс целиком заново. Итог челленджа —
  в `benign_challenged`: версия и проверки в `feedback`, поле `fallback` —
  причина общего вопроса или `null`. Только новые поля (ADR 0008).
- ADR: один новый — «Шлюз отчёта на дайджесте улик». Дополняет 0007
  (побочные ходы видят дайджест, голова по-прежнему — полные ответы),
  строится на 0020 (челленджер заменяет общий вопрос, вопрос остаётся
  фолбэком), 0013 (артефакты отбирает репортёр) и 0018 (проверка
  применяется и к ответу репортёра, фолбэк — черновик). Вводится в первом
  PR, во втором дополняется.

## 6. Цена

Не больше двух лишних вызовов LLM на задачу: репортёр всегда, челленджер на
первый benign. Оба на дайджесте, а не на истории в 70–93 тыс. токенов.
Вызовов runtime не тратят. Время на задачу замеряем против ~6 минут на
закрытом этапе.

## 7. Поставка

Дизайн один, PR — по очереди, чтобы на `practice` было видно, какое
изменение дало какой переворот:

1. **Дайджест + `Review` + челленджер** (#45). Офлайн-стенд режет трейс на
   первом benign `finish_investigation`, восстанавливает ledger из событий
   `tool_call` и запускает только челленджер. Разбиение на dev и holdout
   (по хешу id задачи) фиксируется до работы над промптом. Затем `practice`
   с Qwen3.8 против `20261008T150601Z`, перевороты в обе стороны.
2. **Репортёр** (#39). Стенд сравнивает ссылки черновика и репортёра на тех
   же точках: число артефактов и их пересечение. Настоящий `Q` — только на
   `practice`: неверные вердикты, средний `Q`, число `ir_artifacts`,
   отчёты-заглушки, время на задачу.

[#35](https://github.com/leitosama/sibyl_h0und/issues/35) (поля фазы и
гипотез в шаге) отложен: ошибку фазы «решение» челленджер закрывает одним
вызовом вместо токенов на каждом ходу. Возвращаемся, если после первого PR
на `practice` останутся benign, которые игнорируют проверки челленджера.
