## Коротко

- Организатор: АО «Позитив Текнолоджиз», сообщество FalsePositive.
- ИИ-агент получает алерт («первую улику»), сам обходит граф улик через
  инструменты runtime и выносит вердикт: атака (`malicious`) или легитимная
  активность (`benign`).
- Задачи покрывают весь kill chain, от первичного доступа до кражи данных или
  шифрования. Есть легитимные сценарии, которые выглядят подозрительно. Есть
  шум и ложные ветки.
- Участие индивидуальное: задачи решает участник лично, без других людей.
  Наша трактовка: ИИ-инструменты при разработке агента — это инструменты
  участника, и использовать их можно.
- Ограничений на модели нет. Позиция организаторов: «заодно выясним, правда ли
  модель ничто, а харнесс всё».

## Задачи и оценка

- На зачёте 40 задач. Они скрытые, агент их раньше не видел. **Набор
  инструментов и контекст могут отличаться от тренировочных.**
- Задачи можно решать в любом порядке.
- Платформа оценивает каждую задачу по трём критериям:
  1. верен ли вердикт;
  2. насколько полно проведено расследование, то есть найдены ли нужные
     артефакты;
  3. сколько вызовов инструментов потребовалось: **каждый лишний вызов снижает
     балл**.
- Итог участника — сумма баллов по задачам. Засчитывается выбранная отправка
  каждой задачи, а если выбора нет, последняя.
- Решения проверяются автоматически, но организатор может проверить и вручную.

Наши рабочие допущения, которые проверяем на практике:

- Любой вызов `CallTool` считается вызовом, в том числе ошибочный и следующая
  страница `search`.
- Время решения (`wall_time_seconds`) в балл не входит. Важны точность вызовов
  и вердикт.
- Длину цепочки расследования заранее не знаем, поэтому жёсткий бюджет шагов
  не задаём.

## Ограничения из правил, которые касаются нас

- Нельзя публиковать задачи, способы их решения и собственные решения, кроме
  как для участия в соревновании. Поэтому репозиторий приватный, а данные задач
  и трейсы хранятся вне него (см. [development.md](development.md)).
- Решения передаются организатору по простой неисключительной лицензии.
  Чужие объекты ИС можно использовать, только если это разрешено
  правообладателем (для open-source это лицензия).
- Идентификатор участника — Telegram-аккаунт, указанный при регистрации.

## Протокол runtime

Транспорт — gRPC. Схема лежит в
[`proto/investigation/runtime/v1/runtime.proto`](../proto/investigation/runtime/v1/runtime.proto),
клиент — копия от организаторов в `src/bluesec1_client/`.

```
service ScenarioRuntime {
  rpc CreateRun(CreateRunRequest) returns (Run);              // открыть run
  rpc LeaseTask(LeaseTaskRequest) returns (LeaseTaskResponse); // взять задачу или узнать, что очередь пуста
  rpc CallTool(CallToolRequest) returns (ToolCallResponse);   // вызвать инструмент задачи
  rpc AbortTask(AbortTaskRequest) returns (AbortTaskResponse); // прервать задачу
  rpc CloseRun(CloseRunRequest) returns (CloseRunResponse);   // закрыть run
}
```

Жизненный цикл: `CreateRun` → в цикле `LeaseTask` → `CallTool`… пока ответ не
придёт с `task_result` → `CloseRun`.

### Арена и run

**Арена** — это этап соревнования со своим набором задач: тренировочная
`practice` до 10 октября и зачётная арена 10 октября. Арена задаётся при
создании run'а (`CreateRunRequest.arena`, у нас `SCENARIO_RUNTIME_ARENA`).
Если её не задать, runtime берёт ту, что сейчас открыта. Если арена закрыта,
приходит `COMPETITION_ARENA_CLOSED`.

**Run** — это один проход агента по очереди задач арены:

1. `CreateRun` открывает run. В нём передаются `agent_name`, `label`,
   `model_name` и `metadata`, и всё это видно рядом с run'ом в интерфейсе
   соревнования и на лидерборде.
2. `LeaseTask` выдаёт следующую задачу из очереди. Выбрать конкретную задачу
   нельзя: в запросе есть только `run_id`. Когда задачи кончаются, приходит
   `QueueExhausted`.
3. Задача закрывается вызовом инструмента, который вернул `task_result`, или
   `AbortTask`.
4. `CloseRun` закрывает run. Закрыть можно и раньше, чем кончится очередь.

Ограничения (для каждого — своя причина ошибки):

- **Все ограничения считаются на токен** (`SUBJECT_*`), а не на `agent_name`.
  Токенов можно получить сколько угодно, у каждого своя статистика.
- Одновременно открыт **только один run** (`SUBJECT_ACTIVE_RUN_LIMIT_REACHED`).
  Если агент упал посреди run'а, run остаётся открытым, пока runtime его не
  освободит.
- Частота запуска run'ов ограничена (`SUBJECT_RUN_START_RATE_LIMIT_REACHED`).
- Число одновременно активных задач ограничено и на участника, и на run
  (`SUBJECT_ACTIVE_TASK_LIMIT_REACHED`, `RUN_ACTIVE_TASK_LIMIT_REACHED`). Значения
  неизвестны, исходим из того, что задачи решаются по одной.

Протокол:

- Каждый вызов жизненного цикла несёт idempotency key, каждый вызов
  инструмента — `call_id`. Повторные попытки используют тот же ключ. Всё это
  уже делает `bluesec1_client`.
- Причины ошибок перечислены в `RuntimeErrorReason`. Самые важные:
  `RATE_LIMITED`, `COMPETITION_ARENA_CLOSED`, `RUN_CLOSED`, `TASK_ALREADY_FINISHED`.

Проверяем на практике:

- одинаковы ли задачи и их порядок в каждом новом run'е на `practice`;
- что происходит с задачами, которые остались в очереди после досрочного
  `CloseRun`, и сколько длится пауза между запусками run'ов;
- какой run засчитывается 10 октября («выбранная отправка, иначе последняя»).

### Задача

`LeaseTask` возвращает `PublicTask { task_id, observation }`. В `observation`
лежат алерт (сущности, хост, идентификаторы) и поле `available_tools`:
JSON-строка со списком включённых инструментов и JSON-схемами их аргументов.
**`available_tools` — единственный источник истины об инструментах**, агент
строит вызовы из него, а не из захардкоженного списка.

### Результат

Ответ на вызов, который завершает задачу, содержит `TaskResult`:

| Поле | Смысл |
| --- | --- |
| `completion_reason` | `TERMINATED` (штатно), `TRUNCATED`, `ERROR`, `ABORTED` |
| `total_reward` | итоговый балл задачи |
| `quality_score` | качество: вердикт и полнота |
| `efficiency_score` | эффективность: число вызовов |
| `tool_calls`, `steps_taken` | сколько вызовов и шагов засчитано |
| `wall_time_seconds` | сколько длилась задача |

## Инструменты на арене `practice`

Список снят с базового агента организаторов, на зачёте он может отличаться.

| Инструмент | Что делает |
| --- | --- |
| `search` | поиск подстроки по id и атрибутам: `query` (≥5 символов), `scope` (тип сущности или связи), `time_window`, `page_id`, `sort_order` |
| `get_entity` | сущность и id её входящих и исходящих связей |
| `get_relation` | связь и сущности, которые она соединяет |
| `get_ad_object_info` | объект Active Directory и ссылки для навигации |
| `finish_investigation` | финальный ответ, завершает задачу |

В графе около 40 типов сущностей (Windows и Linux процессы и файлы, реестр,
сервисы, задачи планировщика, WMI, Kerberos, AD, почта, VPN, eBPF и т.д.) и
около 100 типов связей (`parent_of`, `wrote_file`, `connected_to`,
`injected_into`, `logged_on_to`, `created_scheduled_task`, …). Полные списки
есть в `src/sibyl_h0und/models.py`.

### `finish_investigation`

Вердикт `malicious` сдаётся с артефактами для реагирования:

```json
{"verdict": "malicious", "reasoning": "...",
 "ir_artifacts": [{"entity_id": "...", "kind": "host_to_isolate"}]}
```

Возможные `kind`: `host_to_isolate`, `identity_to_rotate`, `persistence_to_remove`,
`cleanup_to_verify`, `file_to_delete`, `network_block`, `mailbox_action`, `other`,
`process_observed`, `registry_observed`, `file_observed`, `mount_observed`,
`lnk_observed`, `ticket_observed`, `identity_observed`, `artifact_observed`.

Вердикт `benign` сдаётся с доказательствами легитимности, которые ссылаются на
наблюдаемые свойства графа:

```json
{"verdict": "benign", "reasoning": "...",
 "legitimacy_evidence": [
   {"anchor": "entity", "entity_id": "...", "property_fields": ["<поле сущности>"]},
   {"anchor": "relation", "relation_id": "...", "property_fields": []}
 ]}
```

Ссылаться можно только на `entity_id` и `relation_id`, которые реально вернул
runtime.
