# 0005. GraphLedger отвечает локально на выдуманные id и повторы

- Статус: Принято
- Дата: 2026-10-05
- Источник: PR #14 (issue #7), коммиты 7a5929f, b54e33a

## Контекст

Базовый агент не помнил пройденный граф: повторял вызовы, звал `get_*` с
выдуманными id (runtime отвечает ошибкой и штрафом, вызов всё равно
считается) и сдавал `finish_investigation` со ссылками, которых runtime не
возвращал.

## Решение

Перед каждым вызовом runtime агент спрашивает детерминированный учёт задачи
`GraphLedger` (`src/sibyl_h0und/ledger.py`):

- id собираются из алерта и из ответов по их форме, а не по имени
  инструмента;
- вызов с неизвестным `entity_id` или `relation_id` не уходит в runtime,
  модель получает ошибку и список известных непройденных id;
- повторный вызов (тот же инструмент и аргументы без `reasoning`) получает
  ответ из кэша;
- `finish_investigation` проверяется локально: все id известны, а
  `property_fields` — ключи объекта, если он был получен по id через `get_*`
  и ответ содержал сам объект. Ключей объекта, известного только из поиска
  или алерта, мы не знаем, и его `property_fields` не проверяем;
- после вызова модель видит `still_open`: что ещё не пройдено.

## Рассмотренные варианты

- Просить модель в промпте не повторяться: не гарантирует ничего.
- Узнавать id по имени инструмента: ломается, если инструменты на зачёте
  другие (см. [0003](0003-tools-from-available-tools.md)).

## Последствия

- `finish_investigation` может ссылаться только на id, которые вернул
  runtime, — это теперь проверяется кодом.
- Обнаружение id эвристическое: любое строковое значение ответа считается
  id, чтобы не отклонять ссылки AD. Ложно отклонённый вызов хуже лишнего.
- По той же причине выдуманное поле объекта, который не открывали через
  `get_*`, проходит локальную проверку, и штрафует его уже runtime.
