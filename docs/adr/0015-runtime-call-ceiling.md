# 0015. Страховочный лимит считает вызовы runtime и оставляет место для отчёта

- Статус: Принято
- Дата: 2026-10-06
- Источник: [issue #28](https://github.com/leitosama/sibyl_h0und/issues/28), развитие [0004](0004-call-economy-without-step-budget.md)

## Контекст

Runtime завершает задачу после 100 вызовов, и задача без
`finish_investigation` получает `Q = 0`. Старый `max_steps` считал ходы
модели, включая ответы, которые дали локально каталог и GraphLedger: при 30
локальных ответах агент сдавался после 70 вызовов runtime. А при
`max_steps = 100` и без локальных ответов runtime мог оборвать задачу раньше
отчёта.

## Решение

- `budget.py` (`CallBudget`) считает только вызовы runtime. Лимит
  `BLUESEC_AGENT_MAX_RUNTIME_CALLS` по умолчанию 95, допустимо от 2 до 99,
  `finish_investigation` входит в лимит. Старая переменная
  `BLUESEC_AGENT_MAX_STEPS` больше не читается.
- Когда сделано `лимит − 1` вызовов, остаётся только `finish_investigation`:
  агент пишет модели об этом отдельным сообщением, схема шага сужается до
  одного инструмента, а другие вызовы отклоняются локально.
- Модель, которая 10 ходов подряд получает только локальные ответы, тоже
  переводится в режим «только отчёт»: она застряла, и отчёт лучше, чем
  бесконечный цикл (см. [0009](0009-run-never-stalls.md)).
- В режиме «только отчёт» у модели 5 ходов. Повторный отчёт после ошибки
  runtime допускается, пока вызов не станет сотым. Если отчёт так и не
  принят, задача прерывается.
- Вход в режим пишется в трейс событием `finish_only`.

## Рассмотренные варианты

- Ограничить общее число ходов модели: снова смешивает ходы и вызовы.
- Прерывать застрявшую задачу: `Q = 0`, а вынужденный отчёт что-то да даёт.
- Лимит 99: не остаётся места повторить отчёт, если runtime его отклонил.

## Последствия

- Локальные ответы не съедают лимит, а длинные расследования доходят до
  отчёта.
- Значение 95 выбрано без замеров: на `practice` задачи укладывались в
  десятки вызовов. Пересмотреть, если трейсы покажут расследования у лимита.
