# 0024. Отчёт ссылается на сущности графа, и kind действует на свой тип

- Статус: Принято
- Дата: 2026-10-09
- Источник: [issue #51](https://github.com/leitosama/sibyl_h0und/issues/51)
  (с правилом «один kind на сущность» из #10), run `practice` `20261009T083824Z`,
  [example-investigation.md](../example-investigation.md) (SC-0045)

## Контекст

GraphLedger ([0005](0005-graph-ledger.md)) считает известным любое строковое
значение из ответов runtime: ложный отказ хуже лишнего вызова. Для отчёта это
слишком мягко. В задачах 019 и 022 run'а `20261009T083824Z` отчёт назвал
`identity_to_rotate` по SID (`S-1-5-21-…`) — это значение свойства
`user_sid` процесса, а не сущность. Такой артефакт ничего не приносит, а
лишний штрафуется ([0013](0013-minimal-report.md)).

Пример организаторов SC-0045 задаёт, на какой тип сущности действует каждый
`kind`: `host_to_isolate` — `host`, `identity_to_rotate` — `windows_user`
(не объект AD), `file_to_delete` — `windows_file` (не процесс),
`network_block` — `network_connection` (не внешний хост),
`process_observed` — `windows_process`. И по одному `kind` на сущность.

Повтор отправленных отчётов шести run'ов 6–9 октября (256 отчётов) нашёл 41
отчётов с такими ссылками: SID, строки `DOMAIN\user`, id объектов AD, id
связи, `temporary_placeholder`; процесс как `file_to_delete` или
`host_to_isolate`, хост как `network_block` или `identity_to_rotate`; два
`kind` на одну сущность. Там же видно, что `host_id` процесса — настоящий id
хоста, даже когда сам хост не открывали (255 таких значений), поэтому он
тоже считается сущностью.

## Решение

- В отчёте (`ir_artifacts` и якоря `legitimacy_evidence`) `entity_id` должен
  быть сущностью из ответа runtime или значением `host_id` (это хост), а `relation_id` —
  связью. Остальные инструменты проверяются мягко, как прежде (0005).
- Таблица пар `kind` → тип из SC-0045 живёт в коде. Отказ — только когда и
  `kind`, и тип сущности есть в таблице и не совпадают. Другие `kind`
  (`*_observed`, кроме процесса, `persistence_to_remove`, `other`, …), другие
  типы (`archive_file`, `windows_service`, …) и сущности без известного типа
  не проверяются: это решает модель. Переименованный на зачёте тип просто
  выпадает из проверки ([0003](0003-tools-from-available-tools.md)).
- Одной сущности — один `kind`.
- Черновик головы с такой ссылкой отклоняется локально **один раз за
  задачу**, как пустой отчёт ([0018](0018-refuse-empty-report-once.md)):
  ответ называет нужный тип и известные сущности этого типа. Следующий
  черновик идёт дальше как есть. Отказ пишется в трейс событием
  `citations_refused`. Если черновик benign ещё ждёт челленджа, отказ и
  вопрос челленджа уходят одним ответом, как в 0018.
- Отчёт репортёра ([0023](0023-reporter.md)) проходит ту же проверку: один
  ход ремонта, потом уходит черновик. Ссылки, которые голова оставила после
  своего отказа, репортёру не вменяются: голова могла знать лучше учёта.
- Промпт репортёра называет те же пары и запрещает ссылаться на значения
  свойств.

## Рассмотренные варианты

- Отклонять, пока ссылки не станут верными: если учёт пропустил форму, в
  которой runtime называет сущность, упорная модель исчерпает ходы режима
  «только отчёт», и задача прервётся с `Q = 0` (0009, 0018).
- Требовать точный тип для каждого `kind`: отклонило бы `archive_file` в
  `file_to_delete` (10 раз в тех же run'ах) и любой новый тип на зачёте.
- Молча выкидывать негодные артефакты: код решал бы за модель, что входит в
  инцидент.

## Последствия

- Ссылки отчёта теперь строже, чем ссылки остальных вызовов; 0005 для отчёта
  уточнён, для остальных вызовов не меняется.
- Отказ стоит одного хода LLM и не тратит вызова runtime. Если репортёр
  дважды ошибся в ссылках, уходит черновик, и переписанный текст теряется.
- Таблицу пар пополняем только по материалам организаторов, а не по наградам
  `practice` (0006).
