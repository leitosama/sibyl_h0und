# 0023. Отчёт пишет репортёр на дайджесте улик, вердикт остаётся за головой

- Статус: Принято
- Дата: 2026-10-09
- Источник: [issue #39](https://github.com/leitosama/sibyl_h0und/issues/39), дизайн [finish-gate.md](../finish-gate.md); развивает [0022](0022-benign-challenger.md), дополняет [0007](0007-compact-llm-context.md), [0013](0013-minimal-report.md), [0018](0018-refuse-empty-report-once.md)

## Контекст

Отчёт пишет голова в конце длинного расследования. На run'е `43acad6a`
(#9) малварные отчёты называли в среднем 9,1 сущности (до 15; до #36 —
3,3–3,7), и задача 024 с верным вердиктом получила `Q = 0,13` из-за лишних
артефактов, а лишние сущности штрафуются (ADR 0013). Две самые длинные
задачи (70–93 тыс. токенов контекста) кончились отчётом-заглушкой; ADR 0018
лечит это одним отказом, но не причину: отчёт пишется на самом длинном
контексте задачи.

## Решение

- Отчёт, который уходит в runtime, сначала пишет **репортёр** — отдельный
  вызов той же LLM с чистым контекстом. Так и в режиме «только отчёт»: там
  контекст головы самый длинный.
- Репортёр видит алерт, описание `finish_investigation` из каталога,
  дайджест улик (ADR 0022), `still_open`, черновик головы и, если был,
  челлендж к benign-черновику. Голова по-прежнему видит полные ответы
  runtime (ADR 0007).
- **Вердикт фиксирован.** Репортёр — роль результата: его задача — чтобы
  отчёт был верным и полным для уже вынесенного вердикта. Отчёт с другим
  вердиктом считается негодным. Это проверка ответа репортёра, а не вето на
  вердикт расследования.
- Ответ — один вызов `finish_investigation` по схеме аргументов из каталога
  задачи (ADR 0003, 0014). Код проверяет его как любой отчёт: аргументы по
  схеме, тот же вердикт, проверка ADR 0018, id и поля свойств через
  GraphLedger (ADR 0005).
- Негодный отчёт возвращается репортёру **один раз** с причиной. После
  второго промаха или если вызов упал, в runtime уходит черновик головы: он
  уже прошёл те же проверки. Задача на этом шаге не останавливается
  (ADR 0009).
- В истории головы остаётся её черновик. Если runtime ответил на отчёт
  репортёра, не завершив задачу, голова видит в ответе `sent_report` —
  что ушло на самом деле. Тот же отчёт второй раз в runtime не уходит:
  GraphLedger отвечает на повтор из кэша (ADR 0005).
- Отбор артефактов и легитимности переходит к репортёру (ADR 0013): он
  оставляет то, что улики связывают с инцидентом, убирает остальное и
  добавляет пропущенное. Промпт — из общих принципов, без сценариев из
  трейсов `practice`.
- Трейс: событие `report_written` с полем `fallback` (причина отправки
  черновика или `null`) и черновиком и отчётом в `payload`; `llm_call` с
  `role: reporter`. Только новые поля (ADR 0008).

## Рассмотренные варианты

- Давать репортёру менять вердикт: может исправить «нет других стадий —
  значит benign», но может и добавить ложные malicious. Вердикт — работа
  головы и челленджера; если `practice` покажет, что репортёр систематически
  видит другое, это отдельное решение.
- Писать отчёт голове, только сжимать её историю после N ходов: рискованно,
  улики, которые модель уже прочла, могут потеряться.
- Проверять отчёт кодом по правилам (сколько артефактов, какие типы): это
  детектор на свойствах, а не решение модели (ADR 0017).

## Последствия

- Один лишний вызов LLM на задачу (два, если нужен ремонт); вызовов runtime
  не тратит.
- Голова может написать слабый отчёт, а репортёр — испортить хороший:
  сравниваем на `practice` неверные вердикты, средний `Q`, число
  `ir_artifacts`, отчёты-заглушки и время на задачу. Офлайн —
  `scripts/replay_side_turn.py --role reporter`: ссылки черновика против
  ссылок репортёра на тех же задачах; настоящий `Q` — только на `practice`.
