# 0019. Связи сущности смотрим поиском по её id

- Статус: Принято
- Дата: 2026-10-07
- Источник: [issue #9](https://github.com/leitosama/sibyl_h0und/issues/9), PR #37; развивает [0005](0005-graph-ledger.md)

## Контекст

На run'е `43acad6a` агент делал в среднем 29 вызовов на задачу при бюджете
задачи около 17 (оценка по `efficiency_score`), из них 458 из 877 —
`get_relation` по одной связи. `get_entity` отдаёт id связей без типов,
поэтому увидеть, что сделал процесс, можно было только открыв каждую. У
Chrome 180 исходящих связей, и модель открывала их в порядке id, то есть
случайной выборкой.

Пробный вызов на `practice` показал: `search` с полным id сущности
возвращает её саму и все связи, где она источник или цель, целиком и с
типами. `scope` с типом связи сужает выдачу до одного типа. Частичный id
не находит ничего.

Одна фраза в системном промпте поведения не изменила: в пяти задачах
следующего прогона модель искала по id один раз. Каждый ход её тянет
`still_open` со списком непройденных связей.

## Решение

- Промпт советует смотреть связи сущности поиском по её полному id, а при
  большом fan-out — ещё и с типом связи в `scope`. Совет условный: если в
  каталоге такой поиск есть (ADR 0003).
- `Investigation` находит в каталоге инструмент по форме аргументов:
  `query` плюс `scope`, в схеме которого упомянуты связи. Имя не
  захардкожено. В ответе на вызов, которым только что открыли сущность с
  непройденными связями, `still_open` получает поле `list_relations_with`:
  один раз на сущность, а не на каждом ходу (ADR 0007).
- GraphLedger считает связь пройденной, если ответ принёс её целиком: тип,
  оба конца и `properties`. Ключи её свойств проверяются в отчёте так же,
  как у связи, открытой по id. Связь без `properties` остаётся
  непройденной.

## Рассмотренные варианты

- Только промпт: проверено, модель совет не применяет.
- Код сам делает поиск по id после каждого `get_entity`: тратит вызов
  runtime без решения модели и не знает, нужен ли он.
- Показывать подсказку на каждом ходу: повторяет один текст в каждом
  сообщении и раздувает контекст.

## Последствия

- Обход связей дешевле: страница поиска (до 10 связей с типами) вместо
  вызова на каждую связь.
- Поиск по id хоста может совпасть со всеми сущностями этого хоста по
  `host_id`; промпт и подсказка велят оставлять только связи, где
  сущность — источник или цель.
- Эффект на число вызовов и вердикты проверяется прогоном `practice`.
