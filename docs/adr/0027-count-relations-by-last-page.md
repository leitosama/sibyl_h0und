# 0027. Связи одного типа считаем по последней странице поиска

- Статус: Принято
- Дата: 2026-10-09
- Источник: разбор задач с `chrome.exe`; развивает [0019](0019-relations-by-id-search.md)

## Контекст

В трейсах 12 задач, где алерт — запуск `chrome.exe` из `explorer.exe`, и все
12 закрыты с Q=0 вердиктом benign. У процесса 3 входящих связи (`parent_of`,
`runs_process`, `hosts`) и 180 исходящих. В run'е `aa50112b` модель прошла
18 страниц поиска по id со `scope` `connected_to`: последняя полная,
`next_page_id` пустой, значит все 180 исходящих — соединения. На это ушло
около 18 вызовов, а вывод о форме активности (один процесс, только
соединения) модель так и не сделала. Третью входящую связь открыли в 1
задаче из 12.

Что показали трейсы:

- на странице поиска 10 результатов, у последней `next_page_id` пустой;
  страница за концом отдаёт пустой список, а не ошибку;
- поиск по полному id без `scope` возвращает саму сущность и все связи, где
  она источник или цель;
- `relation_ids` у `get_entity` полные (встречались списки до 987 id), так
  что число исходящих N известно сразу.

Идея из обсуждения: страница `k = ceil(N / P)` поиска со `scope` одного типа
даёт число связей этого типа `C = (k − 1)·P + len(results)` за один вызов.
Вторая проверка — последняя страница поиска без `scope`,
`T = 1 + входящие + N`, — ничего не добавляет: `T − C − входящие − 1 = N − C`,
а N уже известно. Её не делаем.

## Решение

- `GraphLedger` узнаёт размер страницы P по первой странице, у которой есть
  следующая. По последней странице поиска с полным id полученной сущности,
  `scope` типа связи и без `time_window` он записывает число связей этого
  типа: точное, «не больше» для пустой страницы за концом или «больше» для
  страницы, у которой есть следующая. Страница, где хоть одна связь не
  называет сущность источником или целью (поиск ищет подстроку), не
  считается. Точное число границей не заменяется.
- В `still_open` у сущности появляется `outgoing_by_type`: сколько исходящих
  этого типа и сколько исходящих других типов. Входящие связи того же типа
  вычитаются, когда типы всех входящих известны; иначе ответ просит сначала
  открыть входящие. Тип без связей — «no relations of this type». Число
  больше, чем связей у сущности, помечается как бессмысленное, а не делится
  на отрицательные остатки.
- Если исходящих больше двух страниц (`> 2·P`, до первой страницы P = 10),
  ответ на `get_entity` один раз даёт `count_relations_with`: какую страницу
  запросить, что значит ответ и id входящих связей, которые надо открыть.
- Промпт, фаза 2: если входящих у триггера немного, открыть их все; у занятой сущности
  посчитать преобладающий тип одной страницей вместо листания и искать
  оставшиеся связи других типов.

Код не делает вызовов сам и не оценивает тип связи: он считает то, что
вернул runtime. Что подозрительно, решает модель (ADR 0017).

## Рассмотренные варианты

- Листать все страницы: 18 вызовов на Chrome, проверено в `aa50112b`.
- Два поиска (по типу и без `scope`): второй повторяет N из `get_entity`.
- Список непройденных входящих в каждом `still_open`: повторяет id каждой
  открытой сущности на каждом ходу (ADR 0007). Id входящих даются один раз,
  вместе с советом посчитать.

## Последствия

- На Chrome-подобной сущности обход стоит около 5 вызовов: `get_entity`,
  первая страница, страница `k` и входящие связи. Раньше было 15–35.
- Поиск с `time_window` не считается: его итог несравним с `relation_ids`.
- Если P на зачёте другой, он берётся из первой страницы поиска с `query` и
  `page_id`; порог до неё — 20 исходящих.
- Влияние на вердикт проверяется прогоном `practice` против 12 задач с Q=0.
