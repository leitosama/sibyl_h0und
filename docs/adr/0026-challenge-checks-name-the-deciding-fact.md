# 0026. Проверка челленджера называет решающий факт, голова отвечает наблюдённым значением

- Статус: Принято; ответы головы в `current_state` заменены [0027](0027-challenger-rules-the-verdict.md)
- Дата: 2026-10-09
- Источник: [issue #52](https://github.com/leitosama/sibyl_h0und/issues/52), run `practice`
  `20261009T083824Z`; дополняет [0022](0022-benign-challenger.md),
  [0023](0023-reporter.md) и [0007](0007-compact-llm-context.md)

## Контекст

На run'е `20261009T083824Z` (Qwen3.8-27B, 30 задач) челленджер ADR 0022 часто
называет верную атаку, но голова отклоняет её, не проверив. Проверка сейчас —
это вызов и `refuted_if`: она говорит, *какой вызов* сделать, но не *какой
факт решает*, и голова не обязана сказать, что увидела.

- Задача 004: две проверки из трёх — `already_made`, нового смотреть нечего.
- Задача 006: челленджер описал ретрансляцию входящих соединений, а голова
  ответила «родитель — SYSTEM» и проверила хост назначения, а не время и
  настройку пересылки.
- Задача 010: довод о маяке «закрыли» ещё одним соединением того же вида.
- Задачи 009, 023, 025: проверку «кто создал задачу» закрыли повторным
  открытием той же сущности, а не связи создателя.

По той же выборке у benign-отчётов `Q` падает с числом ссылок (1–3 — около
0,42, 8–10 — около 0,27), а верные по вердикту, но с нулевым `Q` отчёты
ссылаются в основном на связи. Это корреляция на малой выборке.

## Решение

- Проверка челленджера — `look_for` (решающий факт), `confirms_if` (что он
  покажет при атаке), `refuted_if` (что — при её отсутствии) и источник:
  - `call` — вызов инструмента, если факта ещё нет в уликах;
  - `seen` — id объекта из дайджеста и поля свойств, если факт уже собран.
- Код проверяет `call` как прежде (каталог, схема, id, `already_made`;
  ADR 0003, 0005, 0014), а `seen` — по объектам GraphLedger: объект должен
  быть возвращён runtime, поля — у него быть. Голова видит значения этих
  полей из учёта: это повтор уже присланных улик, но только тех нескольких
  значений, на которые опирается проверка, чтобы голова отвечала на тот же
  факт (уточнение 0007). Неподтверждённые поля отбрасываются; проверка без
  подтверждённого поля — целиком. Проверки нумеруются.
- Если проверка негодна (неизвестный id, поле, которого нет, повтор уже
  сделанного вызова или другой проверки), челленджер **один раз** получает
  ответ с причиной по каждой проверке и отвечает заново, как репортёр в
  ADR 0023. Ответ после ремонта принимается как есть: негодные проверки
  отбрасываются, повтор вызова помечается `already_made`.
- Локальный ответ голове просит до повторной сдачи ответить на каждую
  проверку в `current_state` строкой `<n>: <наблюдённое значение> ->
  confirms | refutes | cannot check`. Шлюза нет: следующий отчёт идёт как есть
  (ADR 0009, 0022).
- `before_call` получает `current_state` шага. Состояние шага, который сдаёт
  отчёт после челленджа, — это ответы головы; репортёр (ADR 0023) видит их в
  `challenge.answers` рядом с проверками и обязан учесть каждую в `reasoning`.
- Benign-отчёт репортёра — короткая цепочка **сущностей**: триггер, кто его
  запустил, учётная запись и объект действия, с полями, которые показывают
  легитимность, обычно 3–5 пунктов. Связь цитируется, только когда она сама
  объяснение.
- Промпты — из общих принципов, без программ, портов и типов связей из
  трейсов `practice`. `reward` не используется (ADR 0006).
- Трейс: в `benign_challenged` новые поля проверки; `RecordedDraft` берёт
  `current_state` из события `step`, чтобы офлайн-стенд давал репортёру то же,
  что живой агент. Только новые поля (ADR 0008).

## Рассмотренные варианты

- Оставить `call` + `refuted_if` и только переписать промпт: схема не мешает
  «проверке» повторным вызовом, а голова по-прежнему не называет значение.
- Не принимать отчёт, пока голова не ответит на все проверки: упорная модель
  исчерпает ходы (ADR 0009, 0018).
- Разбирать ответы головы кодом и сверять с `confirms_if`: это решение за
  модель на свойствах (ADR 0017).
- Ограничить число ссылок benign-отчёта кодом: то же, детектор на форме
  отчёта; число остаётся советом в промпте.

## Последствия

- Схема ответа челленджера больше: дольше ответ. Ремонт стоит ещё одного
  вызова LLM, вызовов runtime не тратит. Старые трейсы для стенда репортёра
  читаются без челленджа (общий вопрос).
- Офлайн на `20261009T083824Z` (Qwen3.8-27B, 14 benign под челленджем): доля
  `already_made` — 6 из 42 проверок до, 3 из 40 после (dev 5/24 → 3/23,
  holdout 1/18 → 0/17), `seen` — 6, фолбэков на общий вопрос нет. Без ремонта
  одна новая схема с промптом давала 10 из 38: модель «смотрела, что ещё
  сделала сущность», открывая её повторно.
- Ответы головы попадают только к репортёру; в истории головы
  `current_state` по-прежнему не хранится.
- Сравниваем на `practice` против `20261009T083824Z`: перевороты в обе
  стороны, средний `Q` benign, пунктов на benign-отчёт, доля якорей-связей.
  Офлайн — доля `already_made` и `seen` до и после на dev и holdout.
