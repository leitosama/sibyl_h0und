# Архитектура

## Агент и токены

Агент один: команда `h0und`, код в `src/sibyl_h0und/`. Под `h0und1` и `h0und2`
понимаются токены runtime. Токенов можно получить сколько угодно, у каждого
своя статистика и свои лимиты (run'ы, задачи), подробнее в
[competition.md](competition.md#арена-и-run).

| Токен | Профиль | Когда |
| --- | --- | --- |
| `h0und2` | `.env.h0und2` | разработка и бенчи до 10 октября |
| `h0und1` | `.env.h0und1` | зачёт 10 октября, статистика с чистого листа |

Режимы отладки (полная трассировка, пошаговый режим, человек в цикле)
включаются флагами и работают только на записанных задачах, без runtime. На
арене одну задачу повторить нельзя, поэтому отлаживаемся офлайн.

## Что есть сейчас

Код взят из базового агента организаторов и переименован. Логика пока не
менялась.

```
proto/                         gRPC-схема runtime (от организаторов)
scripts/generate_remote_proto.py  перегенерация src/bluesec1_client/proto/
src/bluesec1_client/           клиент runtime — копия от организаторов, НЕ ПРАВИМ
src/sibyl_h0und/
  cli.py                       точка входа h0und: настройки, run, печать итогов
  settings.py                  настройки из окружения / .env
  agent.py                     SimpleSGRAgent: цикл «одно действие за ход», SYSTEM_PROMPT
  llm.py                       клиент OpenAI-совместимого API со structured output
  trace.py                     JSONL-трейсы run'ов и задач вне репозитория
  ledger.py                    GraphLedger: известные id, кэш вызовов, проверка finish
  flags.py                     флаги: Finding, LevelRule, ScoreRule, FlagBoard
  nextron.py                   таблицы Location / User Context / Form из шпаргалки Nextron
  rules.py                     набор правил по умолчанию
  models.py                    pydantic-схемы шага (NextStep) и аргументов инструментов
tests/                         тесты без сети
```

Цикл базового агента: на каждом шаге модель возвращает `NextStep` (состояние,
план, один вызов инструмента) по строгой JSON-схеме, агент выполняет вызов и
добавляет ответ в историю. Задача заканчивается, когда `finish_investigation`
возвращает `task_result`.

Runtime в каждом ответе повторяет алерт и весь каталог инструментов (~48 КБ),
а новое — только в `last_tool_result`. Поэтому алерт и каталог идут в первое
сообщение один раз, а после каждого вызова в историю попадают только статус,
`last_tool_result` целиком и ошибка. Пошаговый `reward` модели не показываем:
это утечка разметки грейдера, её используем только для офлайн-разбора
трейсов.

Чем базовый агент нам не подходит:

- инструменты зашиты в `models.py`, а на зачёте набор может быть другим;
- он не помнил, какие узлы и связи уже прошёл, и мог повторять вызовы
  (исправлено GraphLedger);
- жёсткий лимит `BLUESEC_AGENT_MAX_STEPS` ≤ 100;
- одна модель делает всё, без ролей и внешних знаний.

## Гипотезы

Это не решения, а то, что проверяем на `practice`. Первым шагом прогоняем
базового агента как есть, записываем трейсы и получаем исходные цифры:
`total_reward`, `tool_calls`, шаги и время на задачу. Стек и роли выбираем
после этого.

Кандидат в стек — **PydanticAI** поверх OpenAI-совместимых endpoint'ов. Если
переходим на него, отключаем значения по умолчанию, которые противоречат
нашим правилам: лимит запросов `UsageLimits(request_limit=50)` (скрытый
бюджет шагов) и параллельное выполнение нескольких tool calls из одного
ответа модели (дубли проходят мимо учёта графа). Альтернатива — развивать
самописный цикл базового агента, он уже даёт полный контроль над вызовами.

Кандидаты в модели: GLM-5.3 через API провайдера, локальная DeepSeek v4.1
Flash, OpenRouter для экспериментов.

### Схема

```
                ┌──────────────────────────── задача (алерт + available_tools)
                ▼
        ┌───────────────┐   runtime-тулы (search / get_* / finish_investigation)
        │  Голова       │──────────────────────────────────────────► runtime
        │  (judge)      │◄──── ответы ───┐
        └──────┬────────┘                │
               │ поручения               │ GraphLedger: пройденные узлы и связи,
               ▼                         │ кэш ответов, запрет повторов
   ┌──────────┬──────────┬──────────┐    │
   │Гипотезёр │IR-аналит.│   TI     │ ───┘ работают только с уже собранными
   └──────────┴──────────┴──────────┘      уликами и внешними знаниями
               │
               ▼
     MCP (VirusTotal и др.), RAG по плейбукам, MITRE ATT&CK, LOLBAS/GTFOBins
```

- **Голова** берёт задачу, единственная ходит в runtime-инструменты и выносит
  вердикт. Так весь бюджет вызовов в одних руках.
- **Исполнители** — роли без доступа к runtime:
  - гипотезёр предлагает версии, что произошло и куда смотреть дальше;
  - IR-аналитик собирает `ir_artifacts` и `legitimacy_evidence`;
  - TI обогащает индикаторы через MCP и базы знаний.
  Состав ролей будет меняться по результатам практики.
- **Динамические инструменты.** Схемы runtime-инструментов строятся из
  `available_tools` каждой задачи, а не из захардкоженных моделей.
- **GraphLedger** (`src/sibyl_h0und/ledger.py`, уже работает) —
  детерминированный учёт пройденного графа на одну задачу. Агент спрашивает
  его перед каждым вызовом runtime:
  - id сущностей и связей собираются из алерта (`trigger_entities`,
    `trigger_relations`) и из ответов по их форме, а не по имени инструмента:
    `relation_ids.incoming`/`outgoing`, `source_id`/`target_id`, `entity_id`,
    `relation_id`, объекты с `id`. Любое строковое значение из ответа тоже
    считается настоящим id, чтобы не отклонять ссылки AD и другие поля;
  - вызов с аргументом `entity_id` или `relation_id`, которого runtime не
    возвращал, не уходит в runtime: модель получает ошибку со списком
    известных непройденных id;
  - повторный вызов (тот же инструмент и те же аргументы без `reasoning`)
    получает прежний ответ из кэша;
  - `finish_investigation` проверяется так же: все `entity_id` и
    `relation_id` должны быть известны, а `property_fields` — ключами
    сущности или связи, если она была получена через `get_*`;
  - после каждого вызова модель видит `still_open`: у каких пройденных
    сущностей остались непройденные связи и какие сущности ещё не открыты.
  Бюджет шагов не задаём, потому что длина цепочек заранее неизвестна.
- **Флаги** (`flags.py`, `nextron.py`, `rules.py`) — детерминированные
  оценки сущностей и связей, которые уже вернул runtime. Лишних вызовов нет,
  модель, сеть и часы не используются: один и тот же узел всегда даёт один и
  тот же результат. Два вида правил:
  - `LevelRule` — шаблон с фиксированным уровнем (`low`/`medium`/`high`),
    например `web_server_spawns_shell`: `w3wp.exe` породил `cmd.exe`;
  - `ScoreRule` — порядковые оценки атрибутов 0 (менее важно), 1 (важно),
    2 (особенно важно). Оценённые атрибуты суммируются, сумма по порогам
    даёт уровень. Атрибут без данных не оценивается и в сумму не входит.
    Так устроена шпаргалка Nextron (Florian Roth, Antivirus Event Analysis
    Cheat Sheet v1.12): таблицы Location, User Context и Form / Type
    пересказаны своими словами. Шпаргалка не говорит, как складывать
    атрибуты, сумма и пороги (`medium` от 3, `high` от 4) — наш выбор, пороги
    калибруем на трейсах. Time не используем, System (роль хоста) пока не
    подключён: роль лежит в отдельной сущности `host`.
  Шпаргалка написана для файлов, на которые сработал антивирус. Для образа
  запущенного процесса каталог `C:\Windows\…` нормален и получает 0, а не 2.
  `FlagBoard` судит каждый узел каждого ответа и сообщает о находке один раз,
  повторно только если ответ принёс больше свойств. Модель видит в `flags`
  только `medium` и `high`, в трейсе (событие `flags`) есть все. Флаги
  совещательные: вердикт выносит модель.
- **Знания.** Open-source плейбуки по типам инцидентов и TI-данные лежат
  локально в векторном хранилище (какое — пока не выбрано). Доступ к внешним
  сервисам — через свои MCP-серверы.
- **Трассировка.** Каждая задача пишет JSONL-трейс в каталог вне
  репозитория (`src/sibyl_h0und/trace.py`), формат и просмотр описаны в
  [development.md](development.md#трейсы). Ответы runtime сохраняются целиком,
  чтобы потом проигрывать задачи офлайн.
- **Время.** На зачёт отведено 4 часа на 40 задач, около 6 минут на задачу,
  и задачи, скорее всего, идут по одной. Каждая дополнительная роль добавляет
  вызовы LLM на шаге, поэтому состав ролей выбираем с учётом замеров времени.

## Инварианты

- `src/bluesec1_client/` и `proto/` не правим, это копия от организаторов.
  Если нужно поведение поверх клиента, пишем обёртку в `sibyl_h0und`.
- В `finish_investigation` попадают только id, которые реально вернул runtime.
- Запуск на арене никогда не ждёт человека.
